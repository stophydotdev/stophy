Set a webhook to get a JSON `POST` when a job reports or a monitor finds something, instead of polling for updates. Every call is signed, so verify the signature before you trust it. Any `2xx` answer says you got it.

## Events

Use `event` to decide how to handle each call. Every source uses the same top-level fields: `id` is the job or monitor, `event` says what happened, `eventId` names the call, and the rest depends on the event. Your `metadata`, if you set it, comes last.

| Source | Events | Set with |
| - | - | - |
| [Crawl](/crawl/async#get-told-with-a-webhook) | `started`, `page`, `completed`, `failed`, `cancelled` | `webhook` on `POST /v1/crawl` |
| [Batch](/batches/overview) | `started`, `page`, `completed`, `failed`, `cancelled` | `webhook` on `POST /v1/batch/scrape` |
| [Agent](/agent/overview) | `started`, `page`, `action`, `completed`, `failed`, `cancelled` | `webhook` on `POST /v1/agent` |
| [Extract](/extract/results) | `completed`, `failed` | `webhook` on `POST /v1/extract` |
| [Monitor](/monitors/webhooks) | `monitor.page`, `monitor.check.completed`, `monitor.changed`, `monitor.failed` | `webhook` on `POST /v1/monitor` |

A job sends `started` when it begins and `page` for each finished page. An agent also sends `action` for each step it takes. The last event is `completed`, `failed` or `cancelled`. For a crawl, `started` gives you `total`. A `page` event gives you the page as it finishes. Use `completed` for the final counts and cost. This example comes from a one-page crawl with custom `metadata`.

```json
{
  "id": "job_q6vkBosI0L0OennuqYa1iw",
  "event": "completed",
  "eventId": "evt_50c7394f-79a4-4863-954d-a9b3e3f8c28c",
  "status": "completed",
  "total": 1,
  "completed": 1,
  "failed": 0,
  "creditsUsed": 1,
  "costUsd": 0.001,
  "metadata": { "project": "docs" }
}
```

Every call has an `eventId` that stays the same when the call is sent again, so you can skip one you already handled. A `page` call holds `result` for a page that was read and `error` for one that failed. When your address falls far behind, a `page` call holds only the page `url` and `resultOmitted: true`. Read that page with the status call of the job. `failed` and `cancelled` have the same fields as `completed`, and `failed` also has a `message`. `costUsd` is what the job was charged so far, in dollars. `creditsUsed` is an older field that counts the same amount in whole steps of $0.002, rounded up. The fields of a monitor event are on [Monitor webhooks](/monitors/webhooks#read-an-event).

## Set a webhook

Send `webhook` as a URL when all you need is an address. Use an object at job creation to set custom headers or metadata, or to pick which events you get. For example, set `"events": ["completed"]` if you only need successful completions.

| Field | Type | Default | Effect |
| - | - | - | - |
| `url` | `string` | none | A public website address that takes a `POST`. Required. |
| `headers` | `object` | none | Up to 10 headers sent with every call. Names are letters, digits and hyphens up to 64 characters, and values up to 1,000 characters without line breaks. `content-type`, `user-agent`, `host`, `content-length` and `stophy-signature` are set by Stophy. |
| `metadata` | `object` | none | An object of up to 4,000 characters that comes back in every call. |
| `events` | `array of string` | all | Which events to send. An extract takes only `completed` and `failed`. |

The headers you set are never kept with a delivery.

## Get the signing secret

`POST /v1/webhook/secret` returns the secret that signs your calls. One account secret signs the calls of every job, and a [monitor](/monitors/webhooks#rotate-the-signing-secret) can have its own. Store it on your server and never in browser code or logs.

<CodeGroup>
```bash cURL
curl -X POST https://api.stophy.dev/v1/webhook/secret \
  -H "Authorization: Bearer $STOPHY_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{}'
```
```typescript TypeScript
const response = await fetch("https://api.stophy.dev/v1/webhook/secret", {
  method: "POST",
  headers: {
    Authorization: `Bearer ${process.env.STOPHY_API_KEY}`,
    "Content-Type": "application/json",
  },
  body: JSON.stringify({}),
});
const { data } = await response.json();
const secret = data.secret;
```
```python Python
import os

import requests

response = requests.post(
    "https://api.stophy.dev/v1/webhook/secret",
    headers={"Authorization": f"Bearer {os.environ['STOPHY_API_KEY']}"},
    json={},
)
secret = response.json()["data"]["secret"]
```
</CodeGroup>

Read the key from `data.secret`. Keep the whole string, with the `whsec_` prefix, as the key. Send `{ "rotate": true }` to replace it with a new secret. The old secret stops signing at once. Update your receiver with the new secret after you rotate. For a planned rotation, you can accept both for a while to handle calls already signed with the old one. If the old secret was exposed, stop accepting it. Reading and rotating cost nothing.

## Verify signatures

Verify calls before you parse or store them. Read the signature from these headers.

| Header | Value |
| - | - |
| `Stophy-Signature` | `t=<unix seconds>,v1=<hex>` |
| `Content-Type` | `application/json` |
| `User-Agent` | `Stophy-Webhook/1` |

`v1` is the HMAC-SHA256, in hex, of `<t>.<body>`, with your secret as the key. `<body>` is the exact text of the request body, so read it before you parse it. Compare in constant time, and reject a call whose `t` is more than 5 minutes from your clock.

Reject a missing or malformed signature. Once it passes verification, store the body by `eventId`. If that ID already exists, answer `2xx` without processing it again. Retries and replays send the same body bytes and event ID. Answer before doing slow work.

## Acknowledge and retry

Answer `2xx` within 5 seconds to stop retries. Redirects are not followed. A call that fails is tried again after 0.5, 2 and 8 seconds, so 4 attempts in all. The calls of one job or monitor are sent in order, one at a time. After 3 deliveries in a row fail, the ones still waiting are skipped.

## Delivery history and retry

Use delivery history to see what reached your receiver and replay a missed event. We keep delivery records for 30 days. Reading and retrying them is free.

| Call | What it does |
| - | - |
| `GET /v1/webhook/deliveries` | Lists deliveries, newest first. Filter with `sourceType` (`batch`, `crawl`, `agent`, `monitor` or `extract`), `sourceId`, `status` (`delivered`, `failed` or `skipped`) and `event`. Send `limit` up to 100 (20 by default), and `cursor` for the next part until it is missing. |
| `GET /v1/webhook/deliveries/{id}` | Reads one delivery with the `payload` that was sent. |
| `GET /v1/webhook/deliveries/{id}/attempts` | Lists every try of one delivery, oldest first. |
| `POST /v1/webhook/deliveries/{id}/retry` | Sends the original payload again. |

The list answers with `data.deliveries`. Each has its `id` (`whd_` and a uuid), `sourceType`, `sourceId`, `event`, `url`, `status`, how many `attempts` it took, and the time and status code of the last one. [Monitor webhooks](/monitors/webhooks#check-deliveries) shows a real list.

If there are no matching deliveries, `data.deliveries` is empty. Read one delivery for `payload`, the exact JSON text we sent. `payloadKeptUntil` tells you when it expires. We keep it for 7 days, but not for zero data retention jobs or after you delete a batch's results.

Read the attempts to see how your address answered. Each attempt has `at`, `ms` for its duration, `status` for the HTTP status, and `error` if it failed. `trigger` is `auto` for automatic attempts and `manual` for a retry you ask for.

When you retry a delivery, we send the original payload once to the current address and headers, signed with the current secret. You can only do this while we still have the payload. If your receiver rejects it, the retry call itself can still succeed. Read `data.attempt` to see the outcome.

## Limits and errors

Check the address and event names before you send a job. Use the error code to see what you can change.

- You get `404 notFound` if the delivery belongs to another account or is more than 30 days old.
- A retry returns `400 invalidRequest` when the payload was not kept, when the delivery is older than 7 days, when the monitor was deleted, or when the monitor has no webhook now.
- A `webhook.url` that is not a public website address returns `400 invalidRequest`.
- `webhook.events` with a name the source does not send returns `400 invalidRequest`. An extract takes only `completed` and `failed`.
- Without an API key, every call here returns `401 apiKeyRequired`.

## Price

Free. Calls Stophy sends, the secret, the delivery reads and the retry cost nothing. The job or the monitor behind a call is charged as usual.
