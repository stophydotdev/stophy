Use a webhook instead of polling when your app needs to act on monitor events. A monitor with a `webhook` sends a signed JSON `POST` to your address when it finds a change and when a check ends. This page covers what monitors send. [Webhooks](/webhooks) covers signatures, retries and delivery history for every call Stophy makes to you.

## Events

Pick the events in `webhook.events` based on whether you need changes, a check receipt or failures.

| Event | Sent when | Payload |
| - | - | - |
| `monitor.page` | A page changed, appeared, or went away. | The page's `url`, `changeStatus`, `at`, and its `diff` and `judgment`. |
| `monitor.check.completed` | A check ended, including a first check and a check that found nothing. | The check's `checkId`, `status`, `summary` and `costUsd`. |
| `monitor.changed` | The same as `monitor.page`. | The same payload. |
| `monitor.failed` | A page could not be read 5 checks in a row, or your balance ran out. | The `reason`. |

A monitor made with `targets` and `schedule` sends `monitor.page` and `monitor.check.completed` when you pick none. A monitor made with the older `url`, `urls` and `interval` fields sends `monitor.changed` and `monitor.failed`.

The first check establishes a baseline for page targets, so it sends no `monitor.page` for those first reads. Search targets can report new results on the first check. It does send `monitor.check.completed`. Subscribe to it to know that checks run, even when nothing changes.

## Set a webhook

Give the monitor a public receiver when you create it, or set `webhook` later with `PATCH /v1/monitor/{id}`. For example, set `"events": ["monitor.page", "monitor.check.completed"]` to get both changes and check receipts. See the request on [Monitors](/monitors/overview#make-a-request).

`PATCH` replaces the webhook as a whole, so send every field you want to keep. Send `"webhook": null` to remove it.

| Field | Type | Default | Effect |
| - | - | - | - |
| `url` | `string` | none | A public website address that takes a `POST`. Required. |
| `events` | `array of string` | see above | The events to send, at least one. |
| `headers` | `object` | none | Up to 10 headers sent with every call. Names are letters, digits and hyphens up to 64 characters, and values up to 1,000 characters without line breaks. `content-type`, `user-agent`, `host`, `content-length` and `stophy-signature` are set by Stophy. |
| `metadata` | `object` | none | An object of up to 4,000 characters that comes back in every call. |

## Read an event

Read `event` to choose how to handle the JSON object. `id` is the id of the monitor, `event` is the event name, `eventId` names the call, and your `metadata` comes last. The call carries `Stophy-Signature` and `User-Agent: Stophy-Webhook/1`.

`changeStatus` is `changed`, `new` or `removed`. A `removed` page has only `url`, `changeStatus` and `at`. A result of a search target also has its `title`. With `json` comparison the event holds `json`, each field before and after. When you set a `goal`, read `judgment` for `meaningful`, `confidence`, `reason` and the `meaningfulChanges` list. A `judgment` with `meaningful: false` is still sent, so you decide what to do with it.

On `monitor.check.completed`, use `monitorId` and `checkId` to look up the check. `finishedAt` tells you when it ended, and `summary` counts the outcomes. `costUsd` is what the check was charged, in dollars. `actualCredits` is an older field that counts the same amount in whole steps of $0.002, rounded up, so a check of $0.001 shows 1.

`monitor.failed` has `reason` and `at`. When one page keeps failing, it also has the `url` and `failures`, which is 5. When your balance runs out, the `reason` is `Your balance ran out, so this monitor is paused.`

Every event has an `eventId` that stays the same when the call is sent again, by a retry or a replay. To ignore an event you have already handled, keep the `eventId` of each one.

## Verify the signature

Verify the signature before you trust or parse the event. Every call has a `Stophy-Signature` header, `t=<unix seconds>,v1=<hex>`. `v1` is the HMAC-SHA256 of `<t>.<body>` with your webhook secret, over the exact bytes of the body. Compute it, compare it in constant time, and reject a call whose `t` is more than 5 minutes from your clock. See [Webhooks](/webhooks#verify-signatures) for the verification steps.

Until you rotate a monitor's secret, its calls are signed with your account secret from `POST /v1/webhook/secret`. After you rotate it, they are signed with the monitor's own secret.

## Rotate the signing secret

Rotate the secret if this monitor needs its own key or its key has been exposed. `POST /v1/monitor/{id}/webhook/rotate-secret` gives one monitor's calls a new secret. The monitor needs a webhook. The samples read the monitor's id from `MONITOR_ID`.

<CodeGroup>
```bash cURL
curl -X POST https://api.stophy.dev/v1/monitor/$MONITOR_ID/webhook/rotate-secret \
  -H "Authorization: Bearer $STOPHY_API_KEY"
```
```typescript TypeScript
const response = await fetch(
  `https://api.stophy.dev/v1/monitor/${process.env.MONITOR_ID}/webhook/rotate-secret`,
  { method: "POST", headers: { Authorization: `Bearer ${process.env.STOPHY_API_KEY}` } },
);
const { data } = await response.json();
console.log(data.id);
```
```python Python
import os

import requests

response = requests.post(
    f"https://api.stophy.dev/v1/monitor/{os.environ['MONITOR_ID']}/webhook/rotate-secret",
    headers={"Authorization": f"Bearer {os.environ['STOPHY_API_KEY']}"},
)
print(response.json()["data"]["id"])
```
</CodeGroup>

Store the new key from `data.secret`, including the `whsec_` prefix. The old secret stops signing this monitor's calls at once. Update the receiver after rotation. For a planned rotation, you can accept both secrets for a while to handle calls already signed with the old one. If the old secret was exposed, stop accepting it. Only this monitor's calls use the new secret. The rest of your jobs keep your account secret. A monitor with no webhook returns `400 invalidRequest`: `This monitor has no webhook, so there is no secret to replace.`

## Check deliveries

Use delivery history when a receiver misses an event. Each call is a delivery. Events of one monitor are sent in order, one at a time. Your address must answer `2xx` within 5 seconds. A call that fails is tried again after 0.5, 2 and 8 seconds, so 4 attempts in all. Redirects are not followed.

List deliveries with `GET /v1/webhook/deliveries` and filter by `sourceType=monitor` and `sourceId`. Add `status=failed` for failures only. This receiver returned `405` for all four automatic attempts. A later manual retry adds another attempt.

```json
{
  "success": true,
  "data": {
    "deliveries": [
      {
        "id": "whd_46b6e278-c841-406d-9760-73efa6fc63be",
        "event": "monitor.check.completed",
        "status": "failed",
        "attempts": 4,
        "lastStatusCode": 405
      }
    ],
    "cursor": "TG3PCyi01794939656464:whd_74bdf4ed-a81e-4b46-a5a3-2fc0844a759f"
  }
}
```

Read one delivery to see the payload that was sent, read its attempts, and send it again with `POST /v1/webhook/deliveries/{id}/retry`. A retry goes to the monitor's current address and secret. See [Webhooks](/webhooks#delivery-history-and-retry).

## Get an email instead

Use email if you want changes without running a receiver. Set `notification.email.enabled` to `true` when you create or update the monitor. Add `"includeDiffs": true` inside `email` if you want the changed text.

| Field | Type | Default | Effect |
| - | - | - | - |
| `email.enabled` | `boolean` | `false` | Send an email when a check finds a change. |
| `email.recipients` | `array of string` | `[]` | Up to 25 addresses. The address of your account gets mail at once. Any other address is sent a confirmation link first and gets nothing else until it is clicked. Every email has a link to stop them. |
| `email.includeDiffs` | `boolean` | `false` | Put the changed text of each changed page in the email. |

The monitor shows each recipient's state in `notification.email.recipientStates`: `confirmed`, `pending` or `unsubscribed`.

## Limits and errors

Check the URL and event names when webhook setup fails.

- `webhook.url` must be a public website address. A private or local address returns `400 invalidRequest`.
- `webhook.events` accepts `monitor.page`, `monitor.check.completed`, `monitor.changed` and `monitor.failed`. Another name returns `400 invalidRequest` with `webhook.events.0: Send one of: monitor.page, monitor.check.completed, monitor.changed, monitor.failed.`
- After 3 deliveries in a row fail, the events still waiting are skipped and show `skipped`.
- A delivery is kept for 30 days, and its payload for 7 days.
