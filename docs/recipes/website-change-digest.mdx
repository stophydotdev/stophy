Send one daily digest of the changes that matter instead of an alert for every edit. A monitor judges changes against your goal. Your receiver stores the events until the digest runs.

You need an API key in `STOPHY_API_KEY` and a public address that can take a `POST`. See the [Quickstart](/quickstart). A page checked once a day costs $0.03 a month.

## 1. Create the monitor

Create a monitor for the pages you want in the digest. Set `goal` to tell the judge which changes matter. `webhook` says where events go. This request watches a page that returns a new identifier on every read, so a later check can show a change. Replace the page with one you care about, and the example address with your receiver. The monthly test schedule avoids daily charges while you set up the receiver. Use `{ "text": "daily" }` for a real digest.

<CodeGroup>
```bash cURL
curl -X POST https://api.stophy.dev/v1/monitor \
  -H "Authorization: Bearer $STOPHY_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Page that changes",
    "targets": [{ "type": "scrape", "urls": ["https://httpbin.org/uuid"] }],
    "schedule": { "cron": "0 0 1 * *" },
    "goal": "Tell me whenever the uuid changes.",
    "webhook": {
      "url": "https://example.com/stophy-hook",
      "events": ["monitor.page", "monitor.check.completed"]
    }
  }'
```

The answer holds the monitor's `id`, here `mon_2f3L73izJTdaA1AQ`, with `judgeEnabled: true` because you sent a goal. Keep the `id` in `MONITOR_ID` for the next steps. The first check starts at once and reads the page for the first time. It sends `monitor.check.completed` and no `monitor.page`. See [Targets](/monitors/targets).

## 2. Receive and store events

Verify the signature before storing an event. Get the account signing secret with `POST /v1/webhook/secret` and keep it in `STOPHY_WEBHOOK_SECRET` on your server. This Bun receiver stores each verified event once and answers `200` before you do any digest work. See [Webhooks](/webhooks#verify-signatures) for the signature format.

```typescript
import { Database } from "bun:sqlite";
import { createHmac, timingSafeEqual } from "node:crypto";

const db = new Database("events.sqlite");
db.run("CREATE TABLE IF NOT EXISTS events (key TEXT PRIMARY KEY, body TEXT NOT NULL)");

const secret = process.env.STOPHY_WEBHOOK_SECRET ?? "";
if (!secret) throw new Error("Set STOPHY_WEBHOOK_SECRET before starting the receiver.");

function verifySignature(key: string, body: string, header: string | null): boolean {
  const signature = /^t=(\d+),v1=([0-9a-f]{64})$/.exec(header ?? "");
  if (!signature) return false;
  const [, timestamp, received] = signature;
  if (!timestamp || !received) return false;
  if (Math.abs(Date.now() / 1000 - Number(timestamp)) > 300) return false;
  const expected = createHmac("sha256", key).update(`${timestamp}.${body}`).digest();
  return timingSafeEqual(Buffer.from(received, "hex"), expected);
}

export async function handle(request: Request): Promise<Response> {
  const body = await request.text();
  if (!verifySignature(secret, body, request.headers.get("Stophy-Signature"))) {
    return new Response("bad signature", { status: 401 });
  }
  const { eventId } = JSON.parse(body);
  db.run("INSERT OR IGNORE INTO events (key, body) VALUES (?, ?)", [eventId, body]);
  return new Response("ok");
}
```

Use `Bun.serve({ port: 3000, fetch: handle })` to run the handler where your monitor can reach it. `id` is the monitor ID. Use `eventId` as the storage key because retries keep it and send the same body.

## 3. See a change

Wait for the first check to set the baseline. Then run a check by hand to see a change without waiting for the schedule.

```bash
curl -X POST https://api.stophy.dev/v1/monitor/$MONITOR_ID/run \
  -H "Authorization: Bearer $STOPHY_API_KEY"
```

The check starts within a minute. The page has changed, so your receiver gets a `monitor.page` call. This example shows the change and the judge's reason. The event also includes `eventId`.

```json
{
  "id": "mon_2f3L73izJTdaA1AQ",
  "event": "monitor.page",
  "url": "https://httpbin.org/uuid",
  "changeStatus": "changed",
  "at": "2026-11-17T18:20:53.979Z",
  "diff": "@@ -1,3 +1,3 @@\n {\n-  \"uuid\": \"0714c38d-30cf-4c11-9c7a-801260afcaba\"\n+  \"uuid\": \"ec011f90-1296-47af-8911-bad9f9aa5314\"\n }\n\\ No newline at end of file\n",
  "judgment": {
    "meaningful": true,
    "confidence": "high",
    "reason": "The uuid value changed, which is exactly what the goal tracks."
  }
}
```

The check cost $0.002: $0.001 for the page and $0.001 for the judge. `GET /v1/monitor/$MONITOR_ID/checks/$CHECK_ID` shows the same result with the diff, whether or not your receiver was up. See [Checks and changes](/monitors/checks-and-changes).

## 4. Build the digest

Run the digest once a day from your scheduler. Read `body` from the `events` table and parse each row as JSON. Keep `monitor.page` events whose `at` is at or after your cutoff, such as the start of the day in UTC. Drop events only when `judgment.meaningful` is `false`. A missing judgment does not rule out a change.

Start the message with the number of changes. For each change, list `changeStatus`, `url` and the judge's `reason`. If there is no reason, use `No judgment.` The example run had one change, with the UUID page's URL and the judge's reason. If nothing matches, send `No changes worth reading in this window.`

## 5. Catch what you missed

Before each digest, look for deliveries your receiver missed. List the failed deliveries and retry them.

```bash
curl "https://api.stophy.dev/v1/webhook/deliveries?sourceType=monitor&status=failed" \
  -H "Authorization: Bearer $STOPHY_API_KEY"
```

For each `id` in `data.deliveries`, call `POST /v1/webhook/deliveries/{id}/retry`. A retry works for 7 days, and your receiver ignores an `eventId` it already stored. Page read failures are not `monitor.page` events. Check the row's `error` in `GET /v1/monitor/{id}/changes`. See [Webhooks](/webhooks#delivery-history-and-retry).

## 6. Clean up

Stop the test monitor when you no longer need it. An active monitor bills on its schedule. Delete the test monitor, then point a new one at your pages.

```bash
curl -X DELETE https://api.stophy.dev/v1/monitor/$MONITOR_ID \
  -H "Authorization: Bearer $STOPHY_API_KEY"
```

## What to check

Verify the receiver and digest with a known change and a duplicate delivery.

- `GET /v1/monitor/$MONITOR_ID/checks` shows a `completed` first check, and your table has its `monitor.check.completed` event.
- A call with a wrong signature gets `401` and stores nothing. The same call twice stores one row.
- The digest lists the changes you made and leaves out a change the judge called noise.
- `GET /v1/monitor/limits` shows the monitors and pages you use, so you know how many more fit.
- `GET /v1/webhook/deliveries?status=failed` is empty on a normal day.
