# stophy-sdk

Official multi-language SDK for the Stophy API - YouTube context for AI agents. The repo ships one TypeScript package (`packages/typescript`, published to npm as `stophy`) and one Python package (`packages/python`, published to PyPI as `stophy`). Both surface the same API surface (video details/transcript/comments/live chat, search, channel, playlist, suggest, and account endpoints) with idiomatic naming per language. A single `openapi.json` at the repo root is the authoritative source for the TypeScript client; the TypeScript `src/generated/` directory is auto-generated from it and must never be edited by hand.

## Conventions

### Source vs generated - what to edit

The TypeScript package has a hard split between generated and hand-written code:

- `packages/typescript/src/generated/` - **never edit by hand**. Every file here is overwritten on `bun run generate`. Add no business logic here. If the shape of the generated output needs to change, edit `openapi.json` or `openapi-ts.config.ts`, then regenerate.
- `packages/typescript/src/index.ts`, `client.ts`, `transport.ts`, `errors.ts`, and `methods/` are hand-written. Keep the public facade thin, endpoint behavior in `methods/`, and HTTP/retry/error behavior in `transport.ts`.

The Python package has no generation step - all source in `packages/python/src/stophy/` is hand-written and must be kept in sync with `openapi.json` manually when the API changes.

### TypeScript

- **Toolchain.** `@hey-api/openapi-ts` for client generation, `tsup` for bundling (ESM + CJS + `.d.ts`), `bun test` for tests, `tsc --noEmit` for type-checking, and Biome for handwritten source/tests.
- **Module format.** ESM primary (`"type": "module"`), CJS secondary. Resolution mode is `Bundler`; imports inside `src/` do not need `.js` extensions.
- **Public surface.** The `exports` map in `package.json` exposes a single entry point (`.`). Do not change the entry structure without bumping a minor version.
- **Tests.** Tests live in `test/typescript/` and are run from the repo root via `bun run test:ts` (which delegates to the workspace `bun test ../../test/typescript`). Tests use a local mock transport - no real API calls in the test suite.
- **`prepublishOnly`.** Running `npm publish` triggers `generate && build` automatically. Never publish without a clean build.

### Python

- **Toolchain.** `uv` for environment and dependency management, `hatchling` as build backend, `pytest` for tests, `ruff` for linting and formatting.
- **Supported Python.** `>=3.9` (pinned in `pyproject.toml`). Keep `from __future__ import annotations` at the top of every source file so `|`-style type hints work on 3.9.
- **Tests.** Tests live in `test/python/` and are run from the repo root via `bun run test:py` (which delegates to `uv --project packages/python run pytest`). Like the TS tests, they use a mock transport - no real API calls.
- **Linting and formatting.** `ruff check` and `ruff format` are the only quality tools. Config lives in `packages/python/pyproject.toml` under `[tool.ruff]`.

### Commit conventions

Work on a new branch for each change; do not make normal feature, fix, or release-infrastructure commits directly on `main`.

This repo uses **Conventional Commits** with a mandatory package scope:

| Scope        | When to use                                                  |
| ------------ | ------------------------------------------------------------ |
| `typescript` | Changes to `packages/typescript/`, `test/typescript/`       |
| `python`     | Changes to `packages/python/`, `test/python/`               |
| `root`       | Changes to `openapi.json`, `package.json`, `.github/`, `scripts/`, repo-wide files |

Examples from the log:

```
feat(typescript): add livechat support
fix(python): handle missing retry-after header
chore(typescript): bump version to 0.1.1
chore(root): add CI workflow
test(python): add retry test suite
```

Use `feat` for new API surface, `fix` for bug fixes, `chore` for version bumps / tooling / config, `refactor` for internal restructuring, `docs` for README / AGENTS changes, `test` for test-only changes. Breaking changes append `!` after the scope: `feat(typescript)!: rename search() to searchVideos()`.

## Regenerating clients from OpenAPI

The TypeScript client is auto-generated from `openapi.json`. Do this whenever the spec changes:

```bash
# From the repo root
bun run generate

# Verify nothing unexpected changed
git diff packages/typescript/src/generated
```

The CI drift check (`Verify generated client is up to date` step) runs `bun run generate` and fails if `src/generated/` differs from the committed state. This means you must regenerate and commit before merging a PR that changes `openapi.json`.

The Python package has no generation step. When `openapi.json` changes, update `types.py`, the relevant module under `methods/`, and both client facades when their public signatures change.

Commit pattern for a spec update:

```
feat(root): add livechat endpoint to openapi.json
feat(typescript): regenerate client with livechat endpoint
feat(python): add livechat support to Python SDK
```

## Adding a language package

1. Create `packages/<language>/` following the existing layout for that language (pyproject.toml for Python, package.json for JS/TS).
2. Add the new package path to the `workspaces` array in the root `package.json` if it is an npm-compatible package.
3. Add corresponding `build:<language>`, `test:<language>`, and `lint:<language>` entries to the root `package.json` scripts so every language is reachable from the root.
4. Add a job to `.github/workflows/ci.yml` (install → lint → type-check → build → test) and a conditional publish job to `.github/workflows/publish.yml` using that registry's trusted publishing mechanism.
5. Update the root `README.md` quick-start section and this `## Layout` tree.
6. The new package should expose the same API surface as the TypeScript and Python packages - same methods, consistent error type, retry behavior.

## Editing the generated TypeScript client

`src/generated/` is owned by `@hey-api/openapi-ts`. Any hand-edit will be overwritten on the next `bun run generate` run. If you need to change behavior:

- **Shape changes** → edit `openapi.json`, then regenerate.
- **Generator config** → edit `packages/typescript/openapi-ts.config.ts`.
- **Extra semantics** → use `client.ts` for the facade, `methods/` for endpoint behavior, and `transport.ts` for HTTP/retry/error handling.

## Releasing / publishing

Each package is released independently.

TypeScript uses Changesets. Add `bun run changeset` to user-visible TypeScript changes, merge the feature PR, then merge the generated `chore(typescript): version package` PR. The version PR updates `packages/typescript/package.json` and `CHANGELOG.md`; merging it publishes `stophy` to npm through trusted publishing. Do not manually bump the TypeScript version or add an npm token.

Python uses explicit `python-v<semver>` tags because Changesets does not version `pyproject.toml`:

```bash
# 1. Update pyproject.toml, uv.lock, and __version__ together
./scripts/bump-version.sh python 0.2.0

# 2. Commit and tag (use the output from bump-version.sh)
git add packages/python/pyproject.toml packages/python/uv.lock packages/python/src/stophy/__init__.py
git commit -m "chore(python): bump version to 0.2.0"
git tag python-v0.2.0

# 3. Push the tag to trigger the publish workflow
git push origin main python-v0.2.0
```

The publish workflow builds the TypeScript client before `npm publish`, so the artifact reflects the current `openapi.json`. npm trusted publishing must point at `.github/workflows/publish.yml` for `stophydotdev/sdk`. For Python, `uv build` produces the wheel and sdist and PyPI trusted publishing uses the same workflow. Neither package uses a long-lived publish token.

## TypeScript package

- Package name on npm: `stophy`. Import as `import { Stophy } from "stophy"`.
- `Stophy` lives in `client.ts`; `index.ts` is the public export barrel.
- Retry logic lives in `transport.ts`. The `maxRetries` and `retryInitialDelayMs` constructor options forward there.
- `StophyError` carries `status`, `code`, `requestId`, and `details`. Catch it to branch on HTTP status or API error code.
- `video()` is overloaded: the `type` discriminant narrows the return `data` type so TypeScript knows the shape without a cast.

## Python package

- Package name on PyPI: `stophy`. Import as `from stophy import Stophy`.
- `Stophy` class in `packages/python/src/stophy/client.py`. Same surface as the TS class, snake_case.
- `StophyError` in `errors.py` carries `status`, `code`, `request_id`, and `details`.
- Typed dicts in `types.py` describe response shapes. They are not validated at runtime - they document shape for static analysis and IDE completion.
- `Stophy` and `AsyncStophy` must expose matching operations. Shared request semantics belong in `transport.py`; endpoint payload construction belongs in `methods/`.

## OpenAPI spec

`openapi.json` at the repo root is the canonical source of truth for the API surface. It drives the TypeScript client generator and documents every endpoint, request body, and response schema for both language teams.

When the API adds or changes an endpoint:

1. Update `openapi.json` first - all other changes derive from it.
2. Regenerate the TypeScript client (`bun run generate`).
3. Update the relevant TypeScript module under `methods/` and its facade method in `client.ts`.
4. Update the Python types, endpoint module, and sync/async facades by hand.
5. Add tests in `test/typescript/` and `test/python/`.
6. Update `README.md` if the public method surface changes.

## Tests

Tests for both packages live in `test/` at the repo root, separated by language. They use a local mock transport (no real API calls, no API key required in CI). Run them with:

```bash
bun run test:ts     # bun test (TypeScript)
bun run test:py     # uv run pytest (Python)
bun run test        # both
```

Keep the test helpers (`test/typescript/helpers.ts` and `test/python/helpers.py`) in sync when you add new mock server capabilities. Both helpers expose a mock HTTP handler that simulates the Stophy API envelope and error responses.
